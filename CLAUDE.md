# VKR Checker — Сервис автоматической проверки магистерских работ

## Описание проекта
Веб-сервис для автоматической проверки ВКР по чек-листу. Студент выбирает образовательную программу, загружает документ (.docx/.pdf), указывает ссылку на базу данных (Яндекс.Диск) — система анализирует работу через языковую модель (OpenAI-совместимый API — на проде Qwen 3.6 35B в Yandex AI Studio) и выдаёт подробный отчёт.

Поддерживаются две образовательные программы НИУ ВШЭ (см. раздел «Поддержка нескольких образовательных программ»):
- **«Интегрированные коммуникации» (ОП ИК)** — магистратура: магистерский проект и магистерская диссертация.
- **«Реклама и связи с общественностью» (ОП РиСО)** — бакалавриат: ВКР в академическом формате.

## Технологический стек
- **Frontend + Backend:** Next.js 14 (App Router), React, TypeScript
- **Стили:** Tailwind CSS
- **БД:** SQLite (через better-sqlite3), файл `data/vkr.db`
- **AI:** Qwen 3.6 35B через **Yandex AI Studio** (OpenAI-совместимый API; модель задаётся в `.env`)
- **Парсинг документов:** mammoth (docx), pdf-parse (pdf), xlsx (Excel)
- **Интеграция:** Яндекс.Диск API (публичные ссылки, без OAuth)
- **Деплой:** **Docker (docker compose) на Yandex Cloud** + Nginx (reverse proxy) + Certbot (SSL)
- **Домен:** вкр-чекер.рф (Punycode: `xn----ctbkawc3be3d.xn--p1ai`)

## Ключевые архитектурные решения

### Три статуса проверки
- **pass** (Зачёт) — все автоматические пункты пройдены, нет ручных
- **fail** (Незачёт) — есть хотя бы 1 автоматически проваленный пункт
- **pending** (Ожидает проверки) — нет проваленных, но есть пункты для ручной проверки (`passed: null`)
- Преподаватель может перевести pending → pass через кнопку «Поставить зачёт» (PATCH /api/attempts)

### Поддержка нескольких образовательных программ

Ось «программа» пронизывает весь ВКР-контур: `ProgrammeId = 'ik' | 'riso'`.

- **`src/lib/programmes.ts`** — единая точка правды: для каждой программы описаны типы работ, список методов исследования, нужна ли презентация, есть ли блок «Анализ конкурентов», минимум методов, пороги объёма, минимальная длительность записей. Форма студента, валидация в API и панель преподавателя читают конфигурацию отсюда — захардкоженных списков в UI больше нет.
- **Форма студента** начинается с «Шаг 1. Образовательная программа» (две карточки). Смена программы сбрасывает тип работы, методы, ссылку на презентацию и язык — у программ разные наборы значений.
- **`/api/check`** принимает `programme` и `workLang`, валидирует, что тип работы предусмотрен программой и что выбрано достаточное число методов.
- **Панель преподавателя** показывает бейдж программы (ИК / РиСО) в колонке «Тип» и колонку «Программа» в Excel-выгрузке. У попыток, сохранённых до появления РиСО, программа выводится из типа работы (`programmeForWorkType`).

Добавление третьей программы = запись в `PROGRAMMES` + ветка в `getChecklist()` + отдельный файл промпта.

### ОП «Реклама и связи с общественностью» (бакалавриат)

Источники: Программа практики ОП РиСО 2025/2026 (ред. 24.03.2026), приложения 31–36 и 39; чек-лист академического руководителя ОП С. В. Катковой (колонка «РИСО»); протокол встречи 10.07.2026. Выжимка требований — `src/lib/methodology/riso-programme-2025.md` (в GPT не передаётся, это источник для сопровождения промпта).

Отличия от ОП ИК:
- **Один тип работы** — `riso_thesis`, ВКР в академическом формате. Нет магистерского проекта.
- **Нет блоков**: ссылка на презентацию, анализ рынка, анализ конкурентов, приложение с ТЗ заказчика, раздел «Обсуждение результатов», требование смешанного дизайна (минимум 1 метод, а не 2).
- **Добавлены пункты**: «Введение» как отдельный обязательный элемент, «Минимум две главы по 2+ параграфа с содержательными названиями», секция «Объём работы», секция «Приложения к тексту работы».
- **Новые методы исследования**: `experiment` (эксперимент) и `ethnography` (наблюдение, кейс-стади, нетнография) — из приложения 35.
- **Длительность записей — 30 минут** (в ОП ИК — 45).
- **Выбор языка работы** (рус/англ) — от него зависит порог объёма.
- Пункт «Выгрузка из программы для статистического анализа» помечен `optional: true` — по регламенту не обязателен и не может дать «незачёт».

### Объём работы — считается программно, не GPT (`src/lib/volume.ts`)

Языковые модели не умеют считать знаки (см. фикс бага ×10 от 11.06.2026 в модуле курсовых), поэтому пункты `volume_total` и `volume_concept` заполняются арифметикой на сервере, а в промпт числа объёма не передаются вовсе — GPT прямо инструктирован их не оценивать.

- Порог: **100 000 знаков с пробелами** (рус.) / **90 000** (англ.), **со сносками**, без титульного листа, содержания, списка литературы и приложений (п. 1.21 Программы практики).
- Концептуальная часть: **не менее 15 000 знаков** (приложение 39, критерий 2). Считается от первой главы до эмпирической — первой главы со словом «эмпирическ» в названии, а если такого нет, до последней главы (`computeConceptCharCount` в `parser.ts`). Считать только «Глава 1 → Глава 2» нельзя: на реальной работе с тремя концептуальными главами это дало 14 133 вместо 81 425 и ложный «незачёт» (Носова, 09.2026). Если глав меньше двух или нумерация нестандартная — `null`, пункт уходит на ручную проверку.
- В интерфейсе показываются обе метрики (с пробелами и без) — чек-лист С. В. Катковой унаследовал от ОП ИК формулировку «без пробелов», Программа практики требует «с пробелами».

### Технические параметры для отзыва руководителя

По договорённости встречи 10.07.2026 автоматизируется техническая часть отзыва (приложение 36), а содержательная оценка и итоговое решение остаются за научным руководителем — чекер оценку не ставит. `/api/check` возвращает поле `technical`:
- **Объём**: знаки с пробелами / без пробелов, знаки сносок, порог, вердикт, объём концептуальной главы.
- **База данных**: сколько аудио/видеофайлов, таблиц и других файлов (формулировки под приложение 36), форматы вне списка приложения 35, ориентировочная длительность записей.

Длительность медиафайлов **оценивается по размеру файла** (публичный API Яндекс.Диска её не возвращает, а сами файлы не скачиваются) и всегда помечена как оценка; соответствующие пункты чек-листа остаются ручными.

### Шаблон отзыва руководителя на ВКР (ОП РиСО)

`GET /api/riso-review?id=<attemptId>` отдаёт .docx по **приложению 36** Программы практики. Кнопка «📄 Скачать шаблон отзыва» — в модалке попытки в панели преподавателя, только для попыток ОП РиСО (`PROGRAMMES[<id>].hasReviewTemplate`).

Генератор — `src/lib/riso-review-doc.ts`. **Принципиальное отличие от Word-отзыва по курсовым (`course-review-doc.ts`): здесь GPT не участвует вообще.** Заполняется только то, что переносится дословно или считается арифметикой:

| Поле отзыва | Источник |
|---|---|
| «Студента(ки) …» | ФИО из формы, родительный падеж (`src/lib/name-case.ts`), «Студента»/«Студентки» — по отчеству |
| Тема работы | поле формы `work_title` |
| «Содержит N аудио/видеофайл(ов), N таблиц, N других файлов» | `DbStats` с Яндекс.Диска |
| «Соблюдение требований к количеству файлов» ДА/НЕТ | число медиафайлов против порога метода (10 интервью / 5 фокус-групп, приложение 35) |
| Объём в знаках с пробелами + вердикт по порогу | `volume_json`, посчитанный при проверке |

Пустыми остаются: все пять содержательных критериев с весами, рекомендуемая оценка, комментарий руководителя, «обязательные структурные элементы», «объём корректного заимствования» (переносится из «Антиплагиата»). В графе «ДА/НЕТ» там, где нужен человек, стоит «—», в комментарии — собранные факты плюс красная пометка «Требуется проверка руководителем». Внизу — служебная плашка «удалите перед подписанием» с перечнем автозаполненных полей.

Состав БД берётся **заново с Яндекс.Диска** на момент выгрузки (студент мог дозагрузить файлы), с фолбэком на снимок `db_stats_json`, сохранённый при проверке.

#### Склонение ФИО (`src/lib/name-case.ts`)
Единственное поле, которое не является переносом или подсчётом. Реализованы только надёжные правила; пол определяется по отчеству (по имени и фамилии не гадаем — «Саша», «Коваль» неоднозначны); при неопределённом поле ФИО остаётся в именительном падеже целиком. Закрытый список исключений для имён с беглой гласной (Пётр → Петра, Павел → Павла, Лев → Льва). Исходное написание печатается в служебной плашке для сверки.

### Чек-лист (`src/lib/checklist.ts`)
- Пункты генерируются динамически через `getChecklist({ programme, type, empMethods, compMethods, usesAI, otherMethodName?, lang? })`
- Поддерживаемые типы работ: `'project'` (магистерский проект, ИК), `'dissertation'` (магистерская диссертация, ИК), `'riso_thesis'` (бакалаврская ВКР, РиСО)
- Каждый пункт имеет `auto: true/false` — автоматическая проверка через GPT/программно или ручная
- `optional: true` — пункт «не обязателен» по регламенту: его невыполнение даёт `passed: null`, а не «незачёт»
- Пункты длительности аудио и качества звука всегда `auto: false` (невозможно проверить программно)

### Методы исследования (`ResearchMethod`)
Доступные методы:
| Метод | Ключ | auto пунктов | Примечание |
|-------|------|-------------|-----------|
| Глубинные интервью | `interviews` | auto: true/false | Пороги: ≥10 файлов, ≥45 мин |
| Фокус-группы | `focus_groups` | auto: true/false | Пороги: ≥5 файлов, ≥45 мин |
| Анализ текстов | `text_analysis` | auto: true | Материалы + кодировочная таблица |
| Опрос | `survey` | auto: true | Выгрузка данных, метаданные, статистика |
| Количественный контент-анализ | `quant_content` | auto: true | Кодировочный лист |
| Мониторинговый анализ | `monitoring` | auto: true | Первичные/вторичные данные |
| Экспертное интервью | `expert_interview` | **auto: false** | Без порогов, всё ручная проверка |
| Эксперимент | `experiment` | auto: true | **Только ОП РиСО.** Выгрузка данных, метаданные, описание рандомизации и размера эффекта |
| Этнографическое исследование | `ethnography` | auto: true | **Только ОП РиСО.** Аудиозаписи бесед / дневник наблюдения / протокол наблюдений |
| Другое | `other` | **auto: false** | Кастомное название метода, ручная проверка |

Пороги длительности записей зависят от программы: ОП ИК — 45 минут, ОП РиСО — 30 минут (приложение 35 Программы практики РиСО). Список методов, доступных студенту, задан в `PROGRAMMES[<id>].methods`.

- При выборе «Другое» в UI появляется обязательное поле для ввода названия метода
- Кастомное название передаётся как `otherMethodName` и используется в текстах пунктов чек-листа
- Для проектов методы также доступны в секции «Анализ конкурентов» (суффикс `_comp`)

### Проверка базы данных
- Яндекс.Диск API используется для получения списка файлов по публичной ссылке
- Рекурсивный обход подпапок до 5 уровней вложенности (`fetchFolderRecursive()` в `yandex-disk.ts`)
- Файлы .xlsx/.csv парсятся (структура таблиц), .docx/.pdf — извлекается текст (превью ~1000 символов)
- Аудиофайлы — только метаданные (имя, размер)
- Описание передаётся в GPT для анализа

### Ссылка на презентацию (только проект)
- GPT проверяет наличие ссылки в документе
- Даже если ссылка найдена — результат `passed: null` (требует проверки преподавателем)
- Содержание презентации невозможно проверить автоматически

### Кнопка «Сохранить результат»
- Проверка НЕ сохраняется автоматически — студент должен нажать «Сохранить результат»
- Это позволяет перепроверять работу без траты попыток (максимум 3)

### Модуль обратной связи
- После проверки студент может оставить текстовый отзыв (необязательно)
- Отзыв сохраняется в поле `feedback` таблицы `attempts`
- Преподаватель видит отзыв в модальном окне деталей попытки

### Авторизация
- **Студент:** клиентская авторизация (без токенов). Логин/пароль задаются при деплое — в публичном репозитории не приводятся.
- **Преподаватель:** клиентская авторизация. Логин/пароль задаются при деплое — в публичном репозитории не приводятся.
- Без авторизации формы недоступны
- Несколько студентов могут работать параллельно с одними учётными данными — конфликтов нет (каждый запрос независим)

### Валидация формы студента
- ФИО: минимум 2 слова (одно слово вызывает ошибку парсинга JSON в OpenAI API)
- Тип работы: обязательный выбор
- Файл: .docx или .pdf, до 50 МБ
- Ссылка на БД: обязательна
- Ссылка на презентацию: обязательна только там, где её требует программа (`requiresPresentation`) — для ОП ИК это магистерский проект
- Методы: минимум по `PROGRAMMES[<id>].minMethods(type)` — 1 для проекта и для ОП РиСО, 2 для магистерской диссертации
- Язык работы: выбирается только на программах с `hasLangChoice` (ОП РиСО); от него зависит порог объёма
- Тема работы: обязательна (≥5 символов) на программах с `requiresWorkTitle` (ОП РиСО) — подставляется в шаблон отзыва руководителя
- Если выбрано «Другое» — название метода обязательно

### Промпт GPT (`src/lib/analyzer.ts`, `src/lib/riso-prompt.ts`)
- Промпты разведены по программам: `buildSystemPrompt(programme)` отдаёт текст ОП ИК либо `buildRisoSystemPrompt()`. Смешивать регламенты нельзя — иначе модель ищет в бакалаврской академической работе «анализ конкурентов».
- В промпте ОП РиСО отдельно оговорено: не оценивать объём (считается программно), ограничивать пояснения фактами из текста и списка файлов, не додумывать содержание и не давать советов — требование протокола 10.07.2026 об ограничении объёма ИИ-комментариев во избежание галлюцинаций и апелляций.
- Системный промпт ОП ИК основан на методических рекомендациях ОП ИК НИУ ВШЭ
- «Кодировочный лист» и «Кодировочная таблица» — синонимы
- Проверка умеренно строгая: отклонение при явном отсутствии элемента или критически малом объёме
- Верификация методов: GPT проверяет, описан ли каждый заявленный метод в тексте работы; если метод заявлен, но не описан — `passed: false`
- Для диссертаций: если заявлено 2 метода, но текст описывает только 1 — `mixed_method: passed: false`
- Поддержка моделей: gpt-4o-mini, gpt-5, gpt-5-nano, o3-mini и др. Автоматическое определение параметров (temperature, max_tokens vs max_completion_tokens)
- На проде модель задаётся как `gpt://<folder-id>/qwen3.6-35b-a3b/latest`: этот идентификатор не подходит ни под одно исключение в `getModelParams()`, поэтому запрос уходит в «новом» стиле — `max_completion_tokens` + `response_format: json_object` + `temperature`. Базовый URL SDK берёт из `OPENAI_BASE_URL` сам, в коде он не задаётся.
- Промпт ОП РиСО использует тот же контракт ответа (JSON-объект `check_id → {passed, note}`), что и ОП ИК, — смены модели не требует

### Панель преподавателя (`src/app/teacher/page.tsx`)
- Сводная таблица всех студентов: ФИО, тип работы, попытки, статусы

### Итоговый отчёт / Статус работы (`src/app/report/page.tsx`)
- Вкладка называется «Итоговый отчет/Статус работы» в шапке всех страниц
- Студент вводит ФИО → **всегда** видит карточку статуса загрузки (загружена ли работа и когда)
- Полные результаты (Зачёт/Незачёт/Ожидает + чек-лист) доступны только после публикации отчёта
- Без авторизации — идентификация только по ФИО
- Поле `tech_comment` не передаётся студенту — только `teacher_review`
- Поиск по ФИО устойчив к trailing spaces: `TRIM(student_name) = TRIM(?)`

### Снапшот при публикации отчёта
- `POST /api/report` сохраняет IDs попыток всех студентов **на момент нажатия** «Создать отчёт» в `report_snapshot_ids`
- Новые работы, поданные после публикации, **не появляются** в отчёте до следующего нажатия «Создать отчёт»
- `GET /api/report` ищет студента только в снапшоте (не во всей таблице `attempts`)
- `DELETE /api/report` очищает и флаг, и снапшот

### Защита эндпоинта отчёта (`src/app/api/report/route.ts`)
- `POST /api/report` требует пароль в теле (`{ password: '<задаётся в коде>' }`) — без пароля возвращает 401
- `DELETE /api/report` закрывает отчёт (очищает флаг и снапшот) — тоже требует пароль
- Пароль хранится в константе `REPORT_PASSWORD` в route.ts

### Кэширование авторизации (`src/lib/authCache.ts`)
- `saveAuth(role)` / `readAuth(role)` / `clearAuth(role)` — localStorage с TTL 24 часа
- Ключи: `vkr-auth-student`, `vkr-auth-teacher`
- При входе сохраняется timestamp; при загрузке страницы проверяется TTL
- Кнопка «Выйти» очищает кэш и сбрасывает состояние

## Модуль курсовой работы (`/course`)

Параллельный контур самопроверки **курсовых работ** студентов ОП ИК. Принципиально отличается от ВКР-модуля: акцент не на pass/fail, а на **интеллектуальных рекомендациях** по улучшению.

### Архитектура модуля
- **Страница студента:** `src/app/course/page.tsx` — авторизация (`student` / `<пароль студента>`, та же как у ВКР), форма (ФИО, **тема работы** — обязательное поле ≥5 символов, тип КР, **ссылка на базу данных Яндекс.Диска — обязательное поле**, файл), результат по «принципу бургера»: статус → общая оценка → **сильные стороны** → что доработать → разбор разделов → **эмпирическая глава двумя блоками** → **анализ базы данных** → приоритетные рекомендации → расширенные. Кнопка **«Отправить работу преподавателю»**. Роль ИИ — **ИИ-консультант** (не «научный руководитель»). На странице есть переключатель **«Я преподаватель»** (см. ниже «Упрощённый преподавательский флоу»).
- **API анализа:** `src/app/api/course/check/route.ts` — `POST /api/course/check`. Парсит файл → вызывает Яндекс.Диск (`getPublicResourceInfo` + `analyzeDatabase` через `analyzeDbWithFallback`, с фолбэком на ссылку из текста работы) для проверки БД → вызывает GPT с фактическим содержимым БД и точным body-объёмом → автоматически пишет попытку в `course_attempts` (каждая загрузка логируется, ссылка на БД сохраняется в поле `db_link`). Принимает доп. поля `mode='teacher'` + `teacherPassword` (пароль `<пароль задаётся в коде>`): в этом режиме файл сразу сохраняется и запись помечается `source='teacher'`.
- **API отправки преподавателю:** `src/app/api/course/submit/route.ts` — `POST`. Сохраняет файл в `data/course-uploads/<attemptId>.<ext>`, проставляет `submitted_at`, `file_path`, `work_title`.
- **API преподавателя:** `src/app/api/course/teacher/route.ts` (GET list/detail; список отдаёт `source`, `hasTeacherReview`, `checkerGrade`), `download/route.ts` (GET оригинал), `reanalyze/route.ts` (POST: повторный GPT-анализ + **повторное обращение к Яндекс.Диску за актуальным состоянием БД** + генерация Word-отзыва; **сохраняет оценку чекера** в `checker_grade`/`checker_grade_rationale`).
- **API загрузки итогового отзыва:** `src/app/api/course/upload-review/route.ts` — `POST` (FormData `attemptId`+`file`). Сохраняет подписанный преподавателем отзыв в `data/course-reviews/<attemptId>.<ext>`, проставляет `teacher_review_path` + `teacher_review_uploaded_at`.
- **API выгрузки архива:** `src/app/api/course/export-reviews/route.ts` — `GET` (force-dynamic). Собирает ZIP (`jszip`) из всех **загруженных итоговых отзывов** (`teacher_review_path IS NOT NULL`); имя каждого файла — ФИО студента + тип (ИКР/КП), с защитой от коллизий.
- **API обратной связи:** `src/app/api/course/feedback/route.ts` — `POST` (тело `{ attemptId, rating, text }`). Сохраняет оценку качества работы сервиса (👍/👎 + текст) от студента или преподавателя в `feedback_rating`/`feedback_text`/`feedback_at`.
- **Удаление работы:** метод `DELETE /api/course/teacher?id=N` — удаляет строку `course_attempts` и связанные файлы с диска (`file_path`, `teacher_review_path`). Используется кнопкой «🗑 Удалить» в сводной таблице.
- **Анализатор:** `src/lib/course-analyzer.ts` — промпт, типы, вызов OpenAI, нормализация ответа. Формат вывода `CourseAnalysisResult` (см. ниже). Роль в промпте — **ИИ-консультант по курсовым работам**; явно запрещены формулировки «как научный руководитель», «как руководитель рекомендую». `EXPECTED_SECTIONS` теперь содержат `synonyms` и `keywords` для семантического сопоставления (бриф ↔ ТЗ, «обзор рынка fashion-ритейла» ↔ «Анализ рынка»). Принимает опциональный `dbAnalysis: DbAnalysisResult` — содержимое БД встраивается в user-промпт.
- **Word-генератор:** `src/lib/course-review-doc.ts` (рендер .docx через `docx`-библиотеку, структура из шаблонов «Шаблон отзыва - ИКР/КП 2026.docx» = Приложение 20.1/20.2 Программы практики) + `src/lib/course-review-prompt.ts` (GPT заполняет поля шаблона). **Жирная красная пометка** «Рекомендуется ручная проверка» рядом с разделами, где невозможна авто-проверка (БД при null-счётчиках, корректность цитирования → Антиплагиат, ИИ-критерии при `yesNo === '—'`). Обоснование оценки (`gradeRationale`) выводится **полноширинным абзацем под таблицей**, в ячейке — только число (`recommendedGrade`). **AI-дисклеймер** про использование ИИ-помощника на основе Chat GPT-5.2 — после подписи руководителя курсивом 10pt. **Объём и вердикт по порогу считаются детерминированно на сервере** (`charCountWithSpaces = bodyCharCountWithSpaces`, строка `volumeRequirementMet` собирается в коде) — GPT числам объёма не доверяет (фикс бага ×10 от 11.06.2026; в промпты числа уходят сырыми целыми).
- **Knowledge base:** `src/lib/methodology/` — каталог `.md`-файлов с методическими материалами. На вход GPT кладётся через `getMethodologyForCourse(type)`, который конкатенирует:
  - `coursework-2024.md` — **актуальная** методичка для 2024–2025 г. набора (структура ИКР/КП, критерии для каждого структурного элемента, стиль и язык, этика). Главное отличие от методички 22/23: ИКР теперь требует полноценную эмпирическую главу (не только дизайн).
  - `programme-2025.md` — Программа практики 2025 г. набора. Регламент: жёсткие пороги объёма (≥90 000 знаков для рус, ≥85 000 для англ), критерии допуска к защите, правила использования ИИ (что можно/нельзя, обязательность раздела «Описание применения генеративной модели»), требования к базам данных по типам исследований (Приложение 19), ГОСТ-стандарты оформления, шкала оценивания с весами (ИКР: введение 0.05 + концепт 0.25 + методы 0.25 + анализ 0.25 + заключение 0.20).
  - `coursework.md` — LEGACY-методичка 22/23 г. набора. По умолчанию НЕ используется; остаётся как fallback на случай отсутствия новых файлов.

  При добавлении новых документов (Гайдбук, программы практики бакалавриата и т.д.) — кладите `.md` в `src/lib/methodology/` и подключайте в `index.ts`.
- **БД:** `src/lib/db-course.ts` + таблица `course_attempts` (отдельная от `attempts`, схема инициализируется лениво в `ensureSchema()`).

### Типы курсовых
- `research` — Исследовательская курсовая (перерастает в МД)
- `project` — Курсовой проект (перерастает в МП)

Ожидаемые разделы определяются константой `EXPECTED_SECTIONS` в `course-analyzer.ts`.

### Формат вывода (`CourseAnalysisResult`)
- `overallSummary` — 2–3 предложения общей оценки
- `readinessStatus` + `readinessStatusText` — общая оценка готовности к зачёту, одно из 5: `ready_for_credit` / `almost_there` / `right_direction` / `fix_then_defend` / `critical_issues`
- `errorClassification` — счётчики по 5 категориям (structural, content, formatting, ai_usage, other)
- `structuralAnalysis` — ожидаемые/отсутствующие/лишние разделы + поразделный разбор (`section`, `present`, `wordCount`, `verdict: ok|too_short|too_long|missing`, `comment`)
- `logicAndCoherence` — `issues` / `strengths`
- `textQuality` — `issues` / `strengths`
- `recommendations` — расширенный список с категориями (`structure | content | logic | text_quality | formatting`)
- `priorityAdvice` — массив приоритетных советов **без верхнего лимита** (мин. 3, типично 5–15). Не обрезается, не дополняется плейсхолдерами.
- `databaseAnalysis` — `{ accessible, fileCount, fileCounts: {audio, tables, docs, other}, issues, strengths, note }`. Заполняется на основе анализа Яндекс.Диск папки + GPT-наблюдений о соответствии методам работы.
- `empiricalChapter` — `{ present, design: {comment, issues, strengths}, analysis: {comment, issues, strengths} }` — эмпирическая глава разбита на два блока (дизайн+инструменты / анализ+интерпретация); отрисовывается двумя подблоками в UI. `null`, если главы нет.
- `disclaimer` — фикс. текст «Итоговое решение по работе принимает научный руководитель»

### Точный подсчёт объёма (`src/lib/parser.ts`)
Функция `computeBodyVolume(text, footnotesText)` ищет границы тела работы:
- **Начало** — позиция заголовка «Введение» (или после титульника по эвристике «ВШЭ» в первых 2000 символов).
- **Конец** — позиция «Список литературы / Список использованных источников / Библиография», иначе «Приложение».
- **Сноски включаются в тело** (по Программе практики). mammoth.extractRawText НЕ извлекает текст сносок (он в `word/footnotes.xml`), поэтому `parseDocx` отдельно достаёт его через `extractDocxNotesText(buffer)` (jszip → `<w:t>` из footnotes/endnotes.xml) и передаёт в `computeBodyVolume`, где объём сносок добавляется к телу. Для PDF сноски уже инлайн в тексте — отдельно не добавляются.
- Возвращает: `bodyWordCount`, `bodyCharCountWithSpaces`, `bodyCharCountNoSpaces`, `appendixWordCount`, `footnoteCharCount`, `volumeBreakdown` (флаги, вкл. `footnotesFound`).
- `bodyCharCountWithSpaces` (тело + сноски) — главная метрика для порога допуска (≥90 000 для рус). Передаётся и в course-analyzer, и в course-review-prompt; в UI/отзыве помечается «с учётом сносок».
